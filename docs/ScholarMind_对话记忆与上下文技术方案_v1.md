# ScholarMind：对话记忆与上下文技术方案（v1）

> **状态**：后端已实现首版（MySQL 表、流式对话写库、Redis 近期消息、Chroma 对话向量、Celery 后置摘要/嵌入；前端透传 `conversation_id`）。细节与运维策略仍以本文为准迭代。  
> **版本**：v1（2026-05）  
> **范围**：多轮对话的持久化、检索增强历史、周期摘要、Prompt 组装顺序及 **Prompt / Prefix KV 缓存** 友好性；不替代 PRD 中文献 RAG（知识库切块）的既有设计，二者在向量侧可用 **不同 collection / 命名空间** 隔离。

---

## 1. 目标与原则

### 1.1 目标

| 目标 | 说明 |
|------|------|
| 多轮可延续 | 用户刷新、换设备（在登录前提下）仍能加载历史会话。 |
| 控制进入模型的 token | 通过「小窗口原文 + 向量检索远历史 + 周期摘要压缩」组合，避免全量历史塞进 prompt。 |
| 数据可信与可恢复 | 关系库为权威来源；向量与缓存可重建。 |
| 延迟与成本 | Redis 热读；稳定前缀尽量命中云厂商 **Prompt / Prefix KV 缓存**（降费、降延迟，视所选 API 能力而定）。 |

### 1.2 原则

1. **MySQL 为唯一事实源（Source of Truth）**；Redis、向量索引均为衍生层。  
2. **写入顺序**：先持久化消息（必要时配合事务或 Outbox），再 **异步** 更新向量与 Redis，避免「能检索到但库里没有」或反向不一致。  
3. **进模型内容结构化**：**稳定前缀 + 易变后缀**，与 KV 缓存机制对齐（见第 6 节）。  
4. **文献 RAG 与对话记忆向量逻辑隔离**：知识库块 vs 对话块分 collection（或等价隔离策略），检索时分别设预算或统一编排但 **metadata 必须区分来源**。

## 2. 总体架构

### 2.1 组件职责

| 组件 | 职责 |
|------|------|
| **MySQL** | 会话、消息行、摘要记录、摘要覆盖游标、向量块元数据（chunk_id、类型、起止 message、hash、embedding 模型版本）、异步任务幂等键。 |
| **Redis** | 最近消息列表、会话元数据、限流、分布式锁、异步任务状态；可选短 TTL 全文热缓存。 |
| **向量数据库** | 存储对话「块」的向量：**滑动窗口原文块**、**周期摘要块**；按当前用户问题（+可选上一轮末句）检索；与文献向量 **分 collection / namespace**。 |
| **摘要 LLM** | 在触发条件满足时，将尚未被摘要覆盖的旧对话压缩为结构化摘要文本，写入 MySQL 并入向量库。 |
| **Embedding** | 与对话块策略一致的模型族；检索与写入使用同一套维度与归一化策略。 |
| **对话 LLM** | 现有流式对话链路；编排层负责按第 6 节顺序组装 messages / 单条超大 prompt（视上游 API 形态而定）。 |

### 2.2 逻辑数据流（简图）

```text
写入：Client → API → MySQL（消息）→ Redis（近期窗口）→ 异步：分块 Embedding → 向量库
                                              ↘ 异步：满足条件 → 摘要 LLM → MySQL → Embedding → 向量库

读取：Client → API → Redis（未命中则 MySQL 回填）
                 → 向量检索（预算内块）+ 最近 K 条原文
                 → 按「稳定前缀 / 易变后缀」组装 → 对话 LLM
```

## 3. 默认参数（v1 敲定值）

以下数值为 **产品默认配置**，上线后可通过环境变量或配置中心覆盖，并应用 **A/B 与离线评测** 迭代。

| 参数 | 默认值 | 含义 |
|------|--------|------|
| **原文窗口 K** | **最近 8 条消息**（按条计数，含 user/assistant） | 整段进入 prompt，保证指代与刚讨论内容。 |
| **原文窗口硬顶** | **合计 ≤ 4000 tokens**（估算即可） | 超出则从 **最旧** 开始移除整条消息，直至满足上限。 |
| **摘要触发（满足其一）** | **每满 10 轮对话** **或** **「未摘要原文」累计 ≥ 8000 tokens** | 轮数与体量双保险。 |
| **摘要冷却** | 一次摘要完成后，再积累 **≥ 6 轮** **或** **≥ 4000 tokens** 未摘要原文，才允许下一次 | 防止短句刷屏导致摘要任务过密。 |
| **检索注入 prompt 预算** | **2000 tokens** | 仅统计「从向量库（及可选关键词路）检索并拼入的块」之和。 |
| **Top-K 与装填** | 先取 **6～10 个候选块**，按相似度 **贪心装填** 直至达到 2000 tokens 上限 | 避免单大块占满预算。 |

### 3.1 检索 Query 建议

- 主查询：当前用户问题文本。  
- 可选增强：上一轮 assistant **末段**（或末条 user）拼接，改善指代消解。  
- 学术场景可选：**BM25 / 关键词** 与向量 **混合检索（RRF 等）**，与文献 RAG 策略对齐时可复用同一套检索编排模块。

## 4. 数据模型建议（MySQL / 向量 metadata）

### 4.1 MySQL（表意级别）

- **会话表**：`conversation_id`，`user_id`，知识库绑定，`created_at` / `updated_at`，可选配置快照。  
- **消息表**：`message_id`，`conversation_id`，`role`，`content`，`created_at`，`trace_id`（若有），可选 `token_est`。  
- **摘要表**：`summary_id`，`conversation_id`，`covers_up_to_message_id`（或序号区间），`summary_text`，`model_version`，`created_at`。  
- **摘要游标**：可在会话表维护 `last_summarized_message_id` / `unsummarized_token_acc`（实现时二选一或组合）。  
- **向量块登记（可选）**：`chunk_id`，类型（`raw_window` / `summary` / `single_message`），`message_id` 起止，`text_hash`，`embedding_model`。

### 4.2 向量库 metadata（每条块）

- `conversation_id`、`user_id`、**块类型**、时间范围、`message_id` 起止。  
- **版本 / 失效**：新摘要覆盖旧区间时，对旧块 **标记废弃** 或双写后删除，避免检索到过期摘要。

### 4.3 Redis Key 约定（示例）

- `conv:{conversation_id}:recent`：最近消息 JSON 列表（长度略大于 K，便于裁剪）。  
- `conv:{conversation_id}:meta`：标题、未读、摘要 checkpoint 等。  
- `job:sum:{conversation_id}`、`job:emb:{chunk_id}`：分布式锁或幂等去重。  
- **TTL**：按产品设定（如 24h～7d 无访问可淘汰热 key，冷读走 MySQL）。

## 5. 写入路径与异步任务

### 5.1 同步路径（单轮对话）

1. 校验鉴权与配额。  
2. **写入 MySQL**：用户消息；助手侧流式结束后再落库完整 assistant 内容（或流式过程中占位行 + 结束更新）。  
3. **更新 Redis**：追加消息、裁剪列表、更新 `updated_at`。  
4. 返回流式响应（与现有 SSE 一致）。

### 5.2 异步路径（建议队列：Celery + Redis）

1. **分块与 Embedding**：对新产生或受影响的原文块生成向量，写入 **对话专用** collection。  
2. **摘要条件检查**：读取游标与累计 token；若满足第 3 节触发条件且通过冷却，投递摘要任务。  
3. **摘要任务**：读未覆盖消息 → 调摘要 LLM → 写 MySQL 摘要表 → 更新游标 → 摘要文本 Embedding → 写向量库。  
4. **失败重试**：指数退避 + 死信队列；**以 MySQL 为准**，提供「按会话重建向量索引」运维能力。

### 5.3 幂等与一致性

- 摘要任务：`conversation_id + covers_range` 作为幂等键，避免重复写入冲突摘要。  
- 向量写入：同一 `chunk_id` 或 `(conversation_id, range, hash)` 去重。  
- 禁止「先 Redis/向量成功、后 MySQL」作为唯一路径；核心事实必须先库。

## 6. Prompt 组装与 Prompt / Prefix KV 缓存

### 6.1 KV 缓存是什么（工程语境）

云厂商提供的 **Prompt / Prefix / Context KV 缓存** 指：在**多请求间**，若 **前缀内容稳定且足够长**（具体规则以厂商文档为准），服务端可复用该前缀对应的 **KV 计算结果**，仅对 **后缀变化部分** 做完整计算，从而降低延迟与部分计费。

**注意**：单次请求内的 Decoder KV 复用由推理框架自动完成；本节特指 **跨请求前缀缓存** 的产品化利用。

### 6.2 推荐拼接顺序（从前到后）

| 顺序 | 块 | 稳定性 | 内容示例 |
|:----:|----|--------|----------|
| **A** | 高稳定、尽量长 | 高 | 系统提示（固定模板，版本号少改）、工具/输出格式说明、**本轮不变的知识库长上下文**（若 KB 固定）。 |
| **B** | 中稳定 | 中 | 会话级长期摘要中 **较少原地修改** 的段落；新摘要建议 **追加段落** 优于频繁改写旧字。 |
| **C** | 每轮变化 | 低 | **向量检索结果**（≤2000 tokens）、**最近 K 条原文**（≤4000 tokens）、**当前用户输入**。 |

### 6.3 实践要点

- **块 A 内避免**：每请求唯一的随机 ID、无必要时间戳、易变调试字段；若必需，置于块 C。  
- **同会话多轮、同 KB**：块 A 越大且字节级一致，越有利于命中前缀缓存；每轮主要变化集中在块 C。  
- **缓存不替代检索**：缓存解决「算过了不用再算」；**检索与 K 窗口**解决「该把哪些话放进上下文」。

## 7. 读取路径（每轮用户发话 → 调模型前）

1. 从 **Redis** 读取最近消息；未命中则 **MySQL** 查询并回填 Redis。  
2. 取 **K = 8** 条消息，应用 **4000 token** 硬顶裁剪。  
3. 构造检索 query（用户当前问题 + 可选上下文）→ **向量检索**（及可选 BM25）→ **贪心装填至 2000 tokens**。  
4. 按第 6.2 节组装 prompt / messages，调用对话模型。  
5. 流式返回；结束后触发第 5.2 节异步任务。

## 8. 风险与对策

| 风险 | 对策 |
|------|------|
| 摘要信息丢失（漂移） | 结构化摘要（结论、未决问题、实体/文献名列表）；始终保留 K 条原文 + 检索 metadata。 |
| 向量与 MySQL 不一致 | 异步失败可重试；定期校验；支持从 MySQL **全量重建** 对话向量。 |
| 多租户隔离 | MySQL 行级按 `user_id`；向量 metadata 强制带 `user_id`，检索过滤；与文献 collection **物理或逻辑隔离**。 |
| 隐私与合规 | 对话是否含敏感内容决定加密、脱敏与留存周期；日志中禁止明文打印长 prompt。 |
| KV 缓存命中率不及预期 | 监控前缀 hash 或厂商「缓存命中」指标；减少块 A 的无谓变动。 |

- **Redis**：解析/任务队列之外，已用于会话近期消息缓存，与 PRD 一致。
